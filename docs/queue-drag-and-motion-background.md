# 0.3.5–0.3.7：队列拖动三次返工、内置/动态背景与壁纸取景

播放列表拖动改了三轮才在真机上站住；背景从「一张内置图」扩到 14 张静态 + 3 张动图 + 3 段视频，
再到 0.3.7 让用户自己**旋转 + 选框**决定露哪一块。本文记录每一轮错在哪、现在为什么不会再错。

## 一、去掉行首拖动把手

队列面板（点底部三条横线打开）每行原来左侧有一个 `DragHandle` 图标 —— 两道横线，既占宽度又和右上角菜单图标容易混。现在整行只保留：序号圆标、标题/作者/时长、圆形播放键、移除键。

拖动改为只走**长按整行**：`detectDragGesturesAfterLongPress` 挂在 `LazyColumn` 上。可点面积比原来的 28dp 把手大得多。
长按落在两行之间 8dp 的缝隙里也会取最近的一行开始拖，不会出现「按到了却没反应」。

## 二、拖动：三代做法与两次翻车

### 0.3.5：把滚动量补进中心

| 做法 | 真机后果 |
|---|---|
| 贴边自动滚动时，把 `scrollBy` 消费的像素**加到被拖行中心**上 | 手指没动，中心却每秒漂上千像素；漂出视口后只能退化成「取最近边缘行」，第一条往下拖瞬间窜到第 30 条 |
| 落点取「离中心最近的一行」，可跨多行换位 | 换位后布局整体重排，中心又落到别的行上，下一帧判到反方向 —— 末条往上拖时页面狂抖 |

### 0.3.6：中心跟手指 + 一次一格

改成「中心只跟手指走、只和紧邻行比中线、越线只挪一格」，单测 6 项全过。
**真机仍然是坏的**：第一条往下拖照样跳到第 26–30 条，从第 26 条往上拖页面剧烈抖动、根本推不上去，
倒数几条也偶发，拖着拖着还会停住。

### 0.3.7：两个根因，两个结构性改法

被前两版忽略的两件事：

| 根因 | 为什么单测没抓到 | 0.3.7 的改法 |
|---|---|---|
| 被拖行留在列表里，用 `translationY` 补偿自己槽位的位移 | 补偿量按**上一帧**的槽位算：换位那一帧 `draft` 已变、布局还没跑，行先跳一下、下一帧再跳回来 —— 60fps 下就是「疯狂抖动」 | 被拖行**移出列表**，画在浮层里，位置只由手指坐标决定；列表原位留一个等高的占位块，其它行不动 |
| 落点判定基于被夹到可视区的中心 | 手指拖出面板后中心被夹成常数，判定就退化成「比它小的都往上换/比它大的都往下换」，一帧一格地连换 | 落点改成**手指当前所在的那一行**，且只从 `visibleItemsInfo` 里选 —— 目标天然被夹在可视区，任何一帧都不可能跨出屏幕 |

```kotlin
// 手指在哪一行，就落到哪一行；目标只可能来自可视区。
internal fun dropTarget(from: Int, y: Float, slots: List<QueueSlot>, inset: Float = 0f): Int? {
    if (slots.isEmpty() || from < 0) return null
    val first = slots.first(); val last = slots.last()
    val lo = first.top + inset
    val hi = last.top + last.height - inset
    if (hi <= lo) return null
    val clamped = y.coerceIn(lo, hi)
    val hit = slots.firstOrNull { clamped < it.top + it.height } ?: last
    return if (hit.index == from) null else hit.index
}
```

配套细节：

- 手指只改 `dragCenter`，换位交给每帧一次的循环做：一次 `onDrag` 事件里绝不连换好几格；
- 贴边自动滚动只滚列表、不动手指位置，滚出来的行会自然落到手指下面，所以「拖到面板外还能继续滚」；
- 浮层行会被夹在面板高度内，手指滑出面板时行停在边缘，不会整行消失；
- 占位块高度取抓取时的实测行高，所以上下行不会因为换位而上下窜；
- 拖动过程中队列被外部改动（切歌、删除）时，只要 `draggedId != null` 就保留草稿，不再把手指下的行弹回原位。

### 单测覆盖

`ui/QueueDragStepTest.kt`（8 项）用 30 行、行高 100、行距 110、视口 800 的模型跑：

- 首条往下拖 640px：每次只挪一格，最终落在第 7 行（下标 6），不会越级；
- 首条往下拖 120px：最多过一行；
- 手指贴底边 + 每帧滚 6px：一路滚到底，全程一格一格，30 条不丢不重；
- 末条往上拖到顶：全程 -1，无反向、无重复；
- 手指不动时连续 40 帧不再换位；
- 可视区外的任意 y（含 -9999 / 99999）：落点一定在可视区首末行之间；
- 手指被拖到面板外很远，逐帧重判也只能停在最后一条可见行，不会跑到列表尾部；
- 空可视区返回 null。

### 已知边界

- 快速甩动时 Compose 把拖动事件按帧合并，极端速度下可能少换一格，松手前补拖即可。
- 顺序保存失败会提示「排序未保存，请重试」，并把草稿恢复成播放器里的真实顺序。

### 0.3.8：视频库「手动排序」也换成同一套

队列修好了，但用户说的「第一条往下拖立刻跳到最后」其实发生在**视频库页面的手动排序**（`LibraryTrackList`），
不是播放队列面板。两处症状同源，代码却是各写一套：

| 层 | 0.3.7 及以前 | 0.3.8 |
|---|---|---|
| 被拖行 | 留在列表里，靠 `translationY = center - slot.offset - size/2` 补偿 | 移出列表画浮层，原位留等高 `Spacer`（与队列一致） |
| 落点判定 | 直接用屏幕坐标 `center` 找「包住它的那一行」 | `dropTarget(from, slot.top + size/2 + residual, slots, inset)` |
| 换位后的记账 | 无，`center` 是绝对值 | `residual = y - targetSlot中心`，只留「手指落在新一行里的偏移」 |

`LazyColumn` 换位时会把**第一个可见项钉在原来的像素上**，槽位坐标整体平移；继续拿屏幕绝对值判断，
就会每帧指到后面几行，首条一路窜到末尾。判定基准改成「被拖行当前槽位中心 + 自上次换位以来的手指位移」后，
单测里的锚定模型（`AnchoredSim`：换位后被拖行始终排在第 0 个槽位）不再连跳。

移植时又发现第二个问题：手势原本挂在**每一行**的 `pointerInput` 上，而拖动一开始这一行就被换成 `Spacer`
离屏，手势节点跟着销毁 —— 第一次换位后拖动就断了（真机表现是「拖一下就自己停下」）。
所以检测器改挂在 `LazyColumn` 上，`onDragStart` 里用 `visibleItemsInfo` 命中最近的一行，
这样换位多少次手势都还在。

`QueueDragStepTest` 从 8 项加到 11 项：首条下拖 4×33px 只挪一格、手指不动 40 帧不再换位、
连续 25×22px 一步一格共 5 格（与 GetAudio 同源）。

### 0.3.9：`key` 让列表自己滚，行高不等让它来回换

0.3.8 装到真机后用户又报了两个更细的现象：

> 把第一条往下拖，文件本身会随着手势往下移，但它原本区域的内容就消失了。而且往下移的位置也不对，
> 明明移到了 7 和 8 中间，显示却还是页面最上方。……当把其他项拖到第一条，然后再拖回、往下移的时候，
> 又会出现首条刚才的毛病，原本第一条的文件位置会留下一大段透明空白，什么都沒有，序号也会出现莫名其妙的问题。

临时在拖动循环里加 `Log.d`，用真机 `input swipe 720 853 720 1600 30000`（30 秒慢速滑动：
前 500ms 位移只有 12px，能稳稳触发长按拖动）抓日志，拿到两条决定性证据：

```
begin  offset=0 size=353 idx=0 first=0/0
from=0 y=353.4 residual=176.9 ptr=388.9 first=0/0  target=1     → 换位
from=1 y=353.5 residual=177.0 ptr=742.0 first=1/0  target=2     ← first 变成 1 了
from=2 y=353.6 residual=177.1 ptr=1095  first=2/0  target=3     ← 又变成 2
```

**一、列表自己在滚。** `itemsIndexed` 带了 `key`，而 `LazyColumn` 换位时会按 key 把「第一个可见项」
钉回原来的像素 —— 拖第一条时，第一个可见项恰好就是被拖行本身，于是**每换一格，列表就自己往下滚一行**
（`firstVisibleItemIndex` 0→1→2，`scrollOffset` 一直是 0）。占位行留在原地、内容被推走，
于是「顶部空一大块」「拖到 7、8 之间画面还停在最上面」，`onDragCancel` 之后残留的滚动还会让序号错位。

修法不是补偿，而是**根本别让 key 钉住**：`itemsIndexed(draft)` 不传 key。key 退化成下标，
换位不改变下标，列表在数据变化时永远不会自己滚（`findIndexByKey` 找到同一个下标）。
行改为按位置复用 —— 行内没有按曲目记忆的状态（`LibraryAudioRow` 里只有 `LocalContext`、
`PlayerHolder` 的全局流），实测无副作用。

**二、相邻行高不等，会在重叠区里来回换。**

```
from=3 ptr=403.9 first=2/236 target=4 slots=3:117 4:400
from=4 ptr=403.6 first=2/236 target=3 slots=3:117 4:470
from=3 ptr=403.3 first=2/236 target=4 …
```

标题两行 / 三行的行高不同（283px vs 353px）。占位行（283）和下面那行（353）交换位置后，
353 那一行从 `400..753` 挪到 `117..470`，手指在 403 —— 两种布局下都「在 353 那一行里」，
于是每帧换一次、再换回来，画面就是疯狂抖。这不是坐标错误，是**双稳态**，必须加死区：

```kotlin
val dir = if (target > from) 1 else -1
val step = 0.5f * minOf(dragHeight, targetSlot.height)
if (dir != lastSwapDir && abs(pointerY - lastSwapY) < step) continue   // 反向换位要再走半行
```

同向换位不受限制，所以往下快拖仍然一步一格跟手；只有「刚换过去又要换回来」才需要额外半行。

**三、判定基准回到手指本身。** 列表不再自己滚，`residual` 就没有存在意义了 ——
直接用 `dropTarget(from, pointerY, slots, inset)`，`pointerY` 就是手指在视口里的真实纵坐标。

队列面板（`ReorderableQueue`）同改：去 key、去 `residual`、加死区，`beginDrag(index)` 改按下标命中
（`onDragStart` 用 `visibleItemsInfo` 的 `index` 而不是 `key`）。

`QueueDragStepTest` 里模拟锚定的 `AnchoredSim` 换成 `StableSim`，四条用例：

| 用例 | 断言 |
|---|---|
| `theGapStaysUnderTheFingerWhileDraggingTheFirstRow` | 手指每挪 3px 都检查一次：占位行的中心离手指不超过一行 |
| `draggingTheFirstRowNeverScrollsTheListByItself` | 全程 `scroll == 0`，一次一格走到最后一格 |
| `stillFingerKeepsTheGapAndTheOrder` | 手指不动 60 帧，占位行和换位次数都不变 |
| `aPinnableGapKeyWouldWalkTheListAway` | 反证：把「钉得住」的锚定行为打开，手指只动 180px 就会连跳 5 格 |

真机验收（0.3.9，同一份代码，真机验收见 GetAudio）：

1. 首条下拖两行 —— 占位行始终在手指下面，顶部立刻由下一行补齐，序号 1..5 连续；
2. 第 5 条拖到第 1 位 —— 占位行一路跟到第一格，顶部不空，没有「拖到顶还停在第 2 格」；
3. 再把第 1 条拖回第 4 位 —— 没有透明空白、没有序号错乱（用户描述的第二个场景）；
4. `am force-stop` 重启后顺序保持。

## 三、内置壁纸：14 张静态 + 3 张动图 + 3 段视频

素材随 APK 打包在 `assets/backgrounds/`，选中即用：不联网、不申请相册权限、不受文件被删影响。

| 目录 | 内容 | 规格 |
|---|---|---|
| `static/` | 14 张静态壁纸 | 长边 2200 的 JPEG（q76，0.3.10 新增那张为 q92 放大），约 380–800 KB/张 |
| `thumb/` | 选择器缩略图 | 320 宽 JPEG，静态 14 张 + 动图/视频各 3 张（`m_` / `v_` 前缀） |
| `motion/` | 3 张动图 | 480×854 动画 WebP，8fps、4 秒循环、q50，约 0.6–1.5 MB/张 |
| `video/` | 3 段视频 | 1080×1920 H.264，24fps、10 秒循环、CRF 26、**无音轨**，约 1.4–2 MB/段 |

0.3.7 把静态图从长边 1280 重新出成 2200：原图都是 16:9，转 90° 后短边要顶到 1440 宽的屏幕，
1280 那版会被放大 2 倍、肉眼可见发虚；2200 版短边 1237，1440 屏上只放大 1.16 倍。

动图与视频都由原图合成：先按 9:16 取竖屏构图（每张单独调过取景位置），再叠一个
`1.0 → 1.10` 的余弦推镜，一圈正好回到起点，所以循环处不跳帧。合成脚本见仓库外的
`gen_backgrounds.sh`（ffmpeg + img2webp）。

选择器是两排横向缩略图（`LazyRow`），缩略图只解码 320px 版本，一屏最多同时挂 4–5 张，
不会因为 14 张全尺寸图同时解码把内存顶爆。

### 0.3.10：「芙宁娜立绘」回来了

0.3.0–0.3.5 的默认背景（`assets/furina.jpg`，1024×1494 竖版立绘）在 0.3.6 整批换壁纸时被删，
名字「芙宁娜」留给了另一张横版图。与 GetAudio 0.9.10 同步加回：从 git 历史取原图，
Lanczos 放大到 1508×2200 + 320×467 缩略图，作为 `still_furina_art`（「芙宁娜立绘」），静态 13 → 14 张。

### 静音是硬性的

- 内置视频编码时就用 `-an` 去掉了整条音轨，文件里根本没有声音；
- 用户自选视频走独立 `ExoPlayer`：`volume = 0` 且 `setAudioAttributes(..., handleAudioFocus = false)`，
  不抢音频焦点，也不会把正在播的音频压低或暂停；
- 动图（GIF/WebP）本身不含音轨。

### 三种来源互斥

内置壁纸、自选图片、自选视频/动图三者只能有一个生效，选任一个都会清掉另外两个；
静态与动态也互斥。偏好里存的是 `still_<id>` / `motion_<id>` / `video_<id>` 这样的唯一键，
因为同一个角色既有静态图又有动图，只靠 id 分不开。

## 四、0.3.7：自己选壁纸露哪一块（旋转 + 选框）

### 问题

内置的 13 张横图原图都是 16:9 的桌面壁纸（0.3.10 加回的「芙宁娜立绘」是唯一一张竖构图）。竖屏手机（9:20）用 `ContentScale.Crop` 铺满时，
按高度放大到 2340 后宽度变成 4160，屏幕上只露出 1080/4160 ≈ 26% 的宽度 ——
人物经常只露半边身子，横构图的图还看着像倒的。

### 做法

`外观 → 显示区域 → 调整显示区域` 打开一个全屏编辑页：

- 中间是一个 **9:19.5 的竖长选框**，框里就是手机实际能显示的范围；
- 单指拖动 = 平移，双指 = 缩放，按钮「旋转 90°」一次转一档（0/90/180/270）；
- 「整张 / 铺满」一键在「整张塞进来（留边）」和「铺满（裁边）」之间切换；
- 「复位」回到正放、铺满、居中。

选完点「完成」，立刻写进 `BackgroundStore`，背景层下一次组合就用新参数。

### 几何模型（纯函数，单测覆盖）

`data/repo/WallpaperFrame.kt`：

```kotlin
data class WallpaperFrame(rotation: Int, zoom: Float, offsetX: Float, offsetY: Float)
```

- `zoom` 是**相对「铺满」的倍数**，1f = 铺满；`minZoom = fit/cover` 是「整张」那一档（横图约 0.26）；
- `offsetX/offsetY` 归一化到**可平移余量**的 -1..1，换设备、换容器尺寸都不用换算；
- `wallpaperGeometry(srcW, srcH, dstW, dstH, frame)` 给出要画多大、两个方向各还能移多远。

渲染在 `ui/components/WallpaperView.kt`：`WallpaperSurface` 用 `requiredSize` 画一个可能比屏幕还大的
Box，`graphicsLayer` 里 `rotationZ` + `translationX/Y`，外层 `clipToBounds`。旋转绕中心，包围盒仍然覆盖整屏。

编辑页和真正的背景层**用的是同一个 `WallpaperSurface`**，所以「选的时候看到什么」就是「回到页面看到什么」。
静态图走 Coil（按画布尺寸采样、后台解码），动图走 `ImageDecoder`，视频走独立 `ExoPlayer`（FILL 不裁切）。

### 存储

每张背景单独记一份：`frame_<key>` = `"旋转|缩放|offsetX|offsetY"`。
内置用 `still_furina` 这类键，自选文件用 `"img:" + uri.hashCode()` / `"mov:" + ...`。
换回原来那张壁纸，之前选的位置还在。

## 五、Wallpaper Engine 壁纸怎么用

Steam 的壁纸引擎把订阅内容放在 `steamapps/workshop/content/431960/<id>/`：

- **视频类壁纸**：目录里直接有 `.mp4`（少数是 `.webm`）。传到手机，在「我的 → 外观 → 选择背景视频」里选中即可，不需要转码。
- **场景 / 网页类壁纸**：`scene.pkg` 是打包格式，手机端没有解析器，读不了。需要先在电脑上用壁纸引擎导出/录制为视频。
- **动态壁纸工程目录**（含 `project.json`）不是视频，不能直接选。

App 不联网、不读 Steam 目录、不解析 pkg，只接受系统文件选择器给出的单个视频/动图文件。
创意工坊内容需要 Steam 账号和 Windows 客户端才能下载，构建包里内置的 3 段视频是按同样的
「慢推镜循环」思路用原图合成的，不是工坊文件本身。
